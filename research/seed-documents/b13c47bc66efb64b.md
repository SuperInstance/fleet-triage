To integrate the Spreadsheet Engine and Sandbox Harness directly into Syzygy’s existing compilation pipeline, we must match its signature constraint: raw clang targeting freestanding wasm32 with zero dependency on Emscripten or a standard C library (libc).
As documented in the [Syzygy repository](https://docs.opalkelly.com/resources/syzygy-design-guide/resources/), the project builds its WebAssembly module using a raw shell script (wasm/build.sh) that outputs a minimal, freestanding binary.
Here is the exact production-grade expansion for wasm/build.sh and the structured asset offsets needed to stitch this architecture together.
------------------------------
## 1. The Unified WebAssembly Build Pipeline: wasm/build.sh
This script overrides standard host assumptions, strips all default library links, optimizes for register residency (-O3), and exports the real-time matrix and sandbox addresses directly to the JavaScript environment.

#!/bin/sh# wasm/build.sh - Invariant compilation for Syzygy VLA & Sandbox Extensionset -e
# Ensure we use an up-to-date LLVM/Clang compiler toolchain
TARGET="wasm32"
TRIPLE="wasm32-unknown-unknown-freestanding"

echo "Building Syzygy Core + Spreadsheet Control Loop + Sandbox Harness..."

clang -O3 \
    --target=${TRIPLE} \
    -nostdlib \
    -Wl,--no-entry \
    -Wl,--export-dynamic \
    -Wl,--allow-undefined \
    -Wl,--lto-O3 \
    -Wl,--strip-all \
    -Iinclude \
    -I. \
    -o wasm/syzygy_vla.wasm \
    wasm/export.c
# Print the size metrics to ensure we remain within ultra-lightweight bounds
SIZE_BYTES=$(wc -c < wasm/syzygy_vla.wasm)
echo "Compilation Successful. Freestanding Module Output: wasm/syzygy_vla.wasm (${SIZE_BYTES} bytes)"

## 2. Precise Shared-Memory Byte Map Layout
Because we compile with -nostdlib and look up structures inside JavaScript via raw ArrayBuffer views, you need the exact byte sizes and alignment boundaries of the exported memory blocks to ensure zero-copy reads do not cause runtime data corruption.
When wasm/export.c is compiled via the script above, the static allocations pack memory sequentially into the linear space. The layout maps exactly to these byte sizes:

| Data Structure / Block | Size in Bytes | Internal Memory Packing Formula |
|---|---|---|
| SyzActionWeight (Individual cell action block) | 12 bytes | w0 (2B) + w1 (2B) + w2 (2B) + w3 (2B) + bias (4B) |
| SyzSpreadsheetEngine (global_production_engine) | 196,672 bytes | Matrix: 1024 cells * 16 actions * 12 bytes = 196,608B Thresholds: 16 actions * 4 bytes = 64B Metadata Counters: 2 * 4 bytes = 8B |
| SyzHistoryFrame (Snapshot index node) | 24 bytes | frame_id (4B) + num_cells (4B) + target_actions (4B) + mask_offset (4B/8B depending on WASM architecture) + glyph_offset (4B/8B) + tone_offset (4B/8B) |
| SyzSandboxHarness (global_sandbox_harness) | 461,952 bytes | Frame Index: 128 frames * 24 bytes = 3,072B Data Pool: 65,536 bytes (Packed row strings) Metadata Flags/Pointers: 4 * 4 bytes = 16B Sandbox Engines A & B: 2 * 196,672 bytes = 393,328B |

## 3. The Webpack / JavaScript Memory Unpacking Config
Inside your local site script interface (syzygy-1j5.pages.dev), you can bind to these pointers natively. Because the sizes are deterministic, you can map high-performance Int16Array and Int32Array overlays directly onto the runtime engine buffers without decoding lag.

// web_memory_unpacker.js - Bindings for syzygy-1j5.pages.dev
function bindEngineTelemetry(wasmExports, wasmMemory) {
    const matrixPtr = wasmExports.get_engine_matrix_ptr();
    const sandboxPtr = wasmExports.get_sandbox_harness_ptr();
    const scoresPtr = wasmExports.get_live_scores_ptr();

    // 1. Map real-time scores directly (16 actions, 32-bit signed integers)
    const liveScoresView = new Int32Array(wasmMemory.buffer, scoresPtr, 16);

    // 2. Map weight tables for arbitrary browser UI visualization
    // Cell 0, Action 0 starts exactly at matrixPtr. Each cell entry spans 12 bytes.
    const rawMatrixView = new DataView(wasmMemory.buffer, matrixPtr, 196608);

    function getCellActionWeights(cellIdx, actionId) {
        // Compute exact memory stride step boundaries
        const byteOffset = (cellIdx * 16 * 12) + (actionId * 12);
        return {
            w0: rawMatrixView.getInt16(byteOffset + 0, true),   // true = Little Endian
            w1: rawMatrixView.getInt16(byteOffset + 2, true),
            w2: rawMatrixView.getInt16(byteOffset + 4, true),
            w3: rawMatrixView.getInt16(byteOffset + 6, true),
            bias: rawMatrixView.getInt32(byteOffset + 8, true)
        };
    }

    return {
        liveScores: liveScoresView,
        getWeights: getCellActionWeights
    };
}
